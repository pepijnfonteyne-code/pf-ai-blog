Week 20 van Claude Code brengt twee primitieven die samen een kwalitatieve sprong betekenen: `claude agents` als unified dashboard voor al je parallelle sessies, en `/goal` als autonome uitvoeringsloop die doorwerkt tot een verifieerbare conditie klopt. Afzonderlijk zijn het handige features. Gecombineerd veranderen ze de manier waarop je werk structureert.

Tot vorige week draaide elk Claude Code-proces in zijn eigen terminaltabblad — je moest elke sessie bijhouden, er naartoe navigeren, en handmatig de volgende prompt sturen. Dat werkt voor één taak, maar schaalt niet. `claude agents` lost het overzichtsprobleem op. `/goal` lost het autonomieprobleem op. Samen bouwen ze de loop die je voor Orion en je Remote Routines nodig hebt.

## Agent View: één scherm voor alle sessies

`claude agents` opent een live overzichtsscherm — één rij per actieve Claude Code-sessie. Elke rij toont vier signalen: session ID, of de sessie op jou wacht, de laatste assistant response, en een timestamp. Drie states: **running**, **blocked on user**, **done**.

```bash
claude agents
```

Vanuit dat dashboard attach je aan een sessie met Enter, en ga je terug naar de lijst met `←`. De sessie blijft doorlopen of wachten — het verlies van de attached terminal stopt niets.

De release voegt ook dispatch flags toe die het starten van background sessies via de CLI formaliseren:

```bash
claude agents \
  --add-dir /home/user/orion \
  --model claude-opus-4-7 \
  --effort xhigh \
  --mcp-config ~/.config/orion-mcp.json \
  --permission-mode auto
```

Met `--cwd <pad>` beperk je de lijstweergave tot de sessies voor een specifieke directory — handig als je meerdere projecten parallel draait. `claude agents --cwd /projects/orion` geeft je alleen de Orion-sessies.

Dit is architectureel interessant: het model dat Anthropic hier inzet persisteert background sessions in de cloud (of lokaal als je offline werkt), en Agent View pollt die state. Dat betekent dat je een sessie kunt starten op je laptop, je laptop kunt sluiten, en de sessie verder loopt — je pikt hem later op via het dashboard. Geen state-server nodig aan jouw kant.

## /goal: autonomous execution tot de conditie klopt

`/goal` is conceptueel eenvoudig maar mechanisch precies wat er altijd ontbrak. Je geeft een verifieerbare afsluitconditie op:

```
> /goal all tests in test/auth pass and the lint step is clean
```

Daarna werkt Claude autonoom, turn na turn. Na elke turn checkt een apart fast model of de conditie klopt. Als niet: Claude start een nieuwe turn. Als wel: het goal wordt gewist en control gaat terug naar jou.

Een overlay panel houdt bij: elapsed time, turn count, en token usage. Dat is niet decoratief — je wil weten hoe duur een autonomous run was voordat je hem vaker gaat starten.

Belangrijk detail: het werkt in interactive mode, met `-p` (non-interactive), én in Remote Control. Dat laatste is de brug naar je automatiseringspipelines. Een Routine kan een sessie starten met `/goal migrate all API calls to v2 and verify no v1 calls remain`, en je ziet in Agent View wanneer die klaar is.

De kwaliteit van je goal-conditie bepaalt de betrouwbaarheid van de autonome run. `/goal` werkt alleen goed als de conditie machine-checkable is. "Tests pass en lint clean" is deterministisch — Claude kan dat zelf verifiëren door het commando te draaien. "Refactor this module to be cleaner" is dat niet. De fout die je wil vermijden: een vage conditie die nooit als klaar wordt herkend, waardoor de loop doorraast tot je token budget op is.

## Hoe pas je dit toe

### Parallel werken aan meerdere PR-reviews

De meest directe toepassing: drie feature branches die reviewed moeten zijn. In plaats van ze sequentieel te verwerken, dispatch je drie background sessies en monitor je de voortgang vanuit Agent View:

```bash
# Open het dashboard
claude agents

# Gebruik dispatch flags voor elke sessie
claude agents --add-dir /projects/app --model claude-opus-4-7 --effort xhigh
# Eenmaal attached: geef het goal mee
# > /goal review PR #142, schrijf samenvatting naar /tmp/pr-142-review.md

# Terug naar lijst (←), volgende sessie dispatchen
claude agents --add-dir /projects/app --model claude-opus-4-7
# > /goal review PR #143...
```

Je werkt door aan iets anders. Zodra een rij van **running** naar **done** gaat, weet je dat de review klaar is — zonder dat je er op hebt gewacht.

### Orion: task dispatch met verificatie via hooks

In Orion kun je `/goal` combineren met `continueOnBlock` in je `PostToolUse` hook — nieuw in v2.1.142. Als Claude een tool aanroept die door je hook wordt geweigerd, stuurt `continueOnBlock: true` de rejection reason terug naar Claude in plaats van de turn te stoppen. Dat is het patroon voor een gecontroleerde autonome agent: als een actie buiten scope valt, leert Claude het en past de aanpak aan zonder dat jij hoeft in te grijpen.

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Bash",
      "hooks": [{
        "type": "command",
        "command": "./validate-action.sh",
        "continueOnBlock": true
      }]
    }]
  }
}
```

Combineer dit met een goal als `/goal alle records in staging.users hebben een migrated_at timestamp` — de migration-loop loopt door, de hook valideert elke stap, en de conditiecheck stopt de loop zodra het klaar is.

### Remote Routines + goal-verificatie + MCP

In Remote Routines (week 16) kon je al sessies dispatchen via schedule of GitHub events. Nu kun je die sessies een `/goal` meegeven als completion condition, zodat de Routine niet klaar is "als Claude klaar denkt te zijn", maar als de conditie aantoonbaar klopt.

Voor je Remote Routines is ook het nieuwe MCP detail interessant: stdio servers ontvangen nu `CLAUDE_PROJECT_DIR` in hun environment. Je MCP server hoeft geen hardcoded pad meer te bevatten — hij leest `process.env.CLAUDE_PROJECT_DIR` en weet waar hij zit. Dat maakt MCP servers die je schrijft voor Orion direct herbruikbaar in andere projecten zonder configuratiewijziging.

### Fast mode: de rekensom

`/fast` draait nu op Opus 4.7 by default. Dat is 2.5x sneller, maar ook 6x duurder: $30/$150 per MTok input/output versus de standaard $5/$25. Een run die normaal $0.50 kost gaat naar $3.

De rekensom is simpel: fast mode lont als de tijdswaarde van 2.5x snellere output de 6x hogere kostprijs overtreft. Voor live debugging of een interactieve sessie waarbij je op de output wacht: ja. Voor een background session met `/goal` die je toch niet afkijkt: nee — gebruik daar standaard Opus 4.7. Wil je terug naar Opus 4.6 voor fast mode: `CLAUDE_CODE_OPUS_4_6_FAST_MODE_OVERRIDE=1`.

## Tot slot

Agent View + `/goal` is geen feature update — het is de primitieve laag waarop je daadwerkelijk parallelle autonome workflows bouwt. Wat ontbrak was niet de modelkwaliteit, maar het controle-interface: één plek om state te zien, één commando om een verifieerbare taak te dispatchen, zonder dat je erbij moet blijven.

De vraag die overblijft: wat is de grens van je goal-condities? "Tests pass en lint clean" is makkelijk machine-checkable. Maar voor taken als "deze module is goed gerefactored" of "dit document is compleet" heb je ofwel een externe validator nodig, ofwel accepteer je dat Claude je om bevestiging vraagt. Dat is het eigenlijke designprobleem voor Orion: definieer doelcondities die zowel ambitieus als deterministisch zijn. Het niveau van je autonome systeem is gelijk aan het niveau van je verificatielogica.
