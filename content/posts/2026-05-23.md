De infrastructuurlaag onder AI-development is deze week in beweging. MCP krijgt zijn grootste specificatiewijziging ooit — het protocol wordt stateless op serverniveau — terwijl Claude Code's plugin-systeem rijper wordt met dependency-grafiek-bewaking. Parallel brengt NousResearch de Hermes Agent Foundation Release uit met een OpenAI-compatible proxy voor OAuth-authenticated providers, en demonstreert Simon Willison met Datasette Agent hoe composable plugin-architectuur eruitziet in productie.

De gemeenschappelijke lijn is opvallend: alles wordt modulairder, minder afhankelijk van centrale state, en meer uitbreidbaar via standaard interfaces. MCP-servers die morgen worden gebouwd kunnen achter een round-robin load balancer draaien. Claude Code-plugins weten van elkaars bestaan. Hermes-providers zijn uitwisselbaar via een gemeenschappelijke interface. Dit zijn geen features — dit zijn architectuurkeuzes die de komende jaren de kaders bepalen.

## Open Source Tools — MCP Release Candidate: stateless protocol, Tasks en MCP Apps

Op 21 mei werd de MCP Release Candidate gelockt voor specificatie versie 2026-07-28. Dit is de meest ingrijpende herziening van het Model Context Protocol since de introductie. De centrale wijziging raakt de deployment-architectuur van elke remote MCP-server: het protocol wordt stateless.

Concreet verdwijnen `Mcp-Session-Id` header en protocol-level sessies. Elke MCP-request moet zelfstandig zijn — de server verwacht geen gedeeld geheugen over requests heen. Verkeer kan nu gerouteerd worden op `Mcp-Method` header, wat betekent dat een gewone round-robin load balancer volstaat. Geen sticky sessions meer, geen gedeelde session stores op infra-niveau.

Dit is een fundamentele keuze die de deployment-complexiteit drastisch verlaagt. Waar je nu bij remote MCP-servers moet nadenken over session affinity en shared state (Redis, een database, whatever), valt dat weg. De tradeoff: applicatielogica die state nodig heeft, moet die state zelf beheren — explicieter, maar ook transparanter.

Twee andere toevoegingen uit de RC zijn architectureel interessant. **Tasks** introduceert long-running work als first-class concept in MCP: een tool-aanroep kan een Task teruggeven die asynchroon voortgang rapporteert in plaats van te blokkeren. Dit lost een structureel probleem op voor agents die operaties uitvoeren die langer duren dan een HTTP-timeout.

**MCP Apps** opent een compleet nieuw design space: server-rendered HTML UIs die worden geserveerd vanuit een MCP-server en weergegeven in sandboxed iframes. Dit betekent dat een MCP-server niet alleen data en tools kan aanbieden, maar ook een interface. Voor Claude Code is dit direct relevant: tools die een visuele component hebben (dashboards, configuratieschermen, diff-views) kunnen straks inline renderen zonder een aparte webapplicatie te hoeven bouwen.

Het validatiewindow loopt 10 weken — Tier 1 SDKs (Python, TypeScript, Java) moeten voor 28 juli de migratie valideren. Bestaande MCP-server implementaties die session-state koppelen aan een `Mcp-Session-Id` moeten die logica migreren naar een expliciete state store. Opt-in op het legacy schema is nog tijdelijk beschikbaar via een revisieheader, maar dat is een noodrem, geen migratieplan.

## Claude Code — Plugin Marketplace: dependency-enforcement en JSON session listing

Claude Code's plugin-ecosysteem krijgt twee concrete verbeteringen uit de updates van week 18-23 mei. De interessantste is dependency-enforcement: `claude plugin disable` weigert als een actieve plugin afhankelijk is van de te disablen plugin, en geeft een copy-pasteable disable-chain hint terug.

Dit klinkt als een detail maar is structureel belangrijk zodra je plugin-stacks bouwt. Stel dat een Orion-workflow bestaat uit plugin A die een MCP-server aanbiedt en plugin B die die server als tool gebruikt. Zonder dependency-enforcement disable je A en breekt B stil. Nu faal je expliciet:

```
$ claude plugin disable orion-mcp-server
Error: plugin 'orion-workflow-runner' depends on 'orion-mcp-server'
To disable both:
  claude plugin disable orion-workflow-runner && claude plugin disable orion-mcp-server
```

De copy-pasteable hint is praktisch: je hoeft niet handmatig de dependency-graph te reconstrueren.

De tweede verbetering is JSON output voor session listing:

```bash
claude sessions --format json | jq '.[] | select(.status == "blocked")'
```

Dit maakt externe monitoring van Claude Code-sessies mogelijk: een CI/CD pipeline kan blockers detecteren, een dashboard kan sessie-status aggregeren, of een Orion-component kan reageren op sessies die input nodig hebben. Gecombineerd met de vernieuwde Plugin Discover en Browse screens — die nu commands, agents, skills, hooks en MCP/LSP servers tonen vóór installatie inclusief kostenindicaties — wordt het plugin-systeem serieus bruikbaar als infrastructuurlaag voor complexere setups.

## Hermes / Open Source — Foundation Release: xAI Grok OAuth en OpenAI-compatible proxy

NousResearch bracht op 16 mei 'The Foundation Release' van Hermes Agent uit: 808 commits, 633 gemergte PRs. De meest pragmatische toevoeging voor builders is de **OpenAI-compatible lokale proxy** voor OAuth-authenticated providers.

Het probleem dat dit oplost: providers die OAuth gebruiken (zoals xAI Grok met zijn 1M context window) zijn niet direct aanroepbaar via de standaard OpenAI SDK-interface die de meeste tooling verwacht. Hermes Agent plaatst een lokale proxy tussen jouw tooling en de provider:

```yaml
# ~/.hermes/providers.yaml
providers:
  - name: grok-1m
    type: xai
    auth: oauth
    context_window: 1000000
    proxy:
      port: 8080
      openai_compatible: true
```

Na configuratie is `http://localhost:8080` een standaard OpenAI-compatible endpoint. Elke tool die met OpenAI werkt — LangChain, je eigen SDK-code, MCP-servers met LLM-calls — spreekt nu ook xAI Grok aan zonder code-wijzigingen. Model-switching wordt hiermee een configuratiewijziging in plaats van een refactoring.

`x_search` als first-class tool is de andere relevante toevoeging: real-time X/Twitter zoeken als geïntegreerde agent-capability, niet als externe API die je zelf moet draaien. Nuttig voor agentic workflows die real-time informatie nodig hebben naast statische tool-resultaten.

Interessant vergelijkingspunt: Hermes Agent heeft ook een `/goal`-implementatie, gelijktijdig met Claude Code's /goal-feature (beide in mei gelanceerd). Beiden definiëren een persistente stuurvariabele die de agent herbevraagt totdat een evaluatieconditie True retourneert. De implementaties zijn onafhankelijk ontwikkeld maar convergeren naar hetzelfde patroon — wat suggereert dat dit een natural interface boundary is voor autonome workflows, eerder dan een toevallige feature.

## AI Builders — Simon Willison: Datasette Agent en de composable plugin-architectuur

Simon Willison publiceerde op 21 mei Datasette Agent: een AI-agent over Datasette-databases die via plugins uitbreidbaar is. De architectuur is het interessantste deel: elke agent-capability is een afzonderlijke Python package.

```bash
pip install datasette-agent
pip install datasette-agent-charts          # Observable Plot visualisaties
pip install datasette-agent-openai-imagegen # ChatGPT Images 2.0 integratie
pip install datasette-agent-sprites         # Sandboxed code execution via Fly Sprites
```

De agent laadt beschikbare plugins dynamisch en kent zijn eigen capabilities via plugin discovery. Een query over een dataset kan resulteren in een chart, een gegenereerde afbeelding, of code die wordt uitgevoerd in een persistent Fly Sprites sandbox — afhankelijk van welke plugins geïnstalleerd zijn. Dit is opt-in tool composition in productie.

De Fly Sprites integratie is architectureel het meest interessante stuk: een persistent code execution sandbox als agent-tool. Niet een wegwerpcontainer die start en stopt, maar een sandbox die state bewaart tussen aanroepen. Willison demonstreert hiermee het 'agentic persistent workspace' patroon — vergelijkbaar met wat Claude Code's eigen execution environment doet, maar als standalone service die je per agent-instantie kunt inzetten.

Het compositie-principe sluit direct aan op de MCP RC-richting en de Claude Code plugin-dependency updates: geen monolithische agent met alle capabilities hardcoded, maar een kernel met expliciet gedeclareerde, verwisselbare uitbreidingen. De complexiteit zit in de discovery- en dependency-laag, niet in de agent zelf.

## Tot slot

De stateless MCP-spec, de Hermes OAuth-proxy, de Claude Code dependency-graphs en de Datasette plugin-compositie zijn vier uitdrukkingen van hetzelfde principe: expliciete interfaces, geen verborgen gedeelde state. Zodra je state verplaatst van de infrastructuurlaag naar de applicatielaag, kun je horizontaal schalen. Zodra je capabilities verplaatst van monolithische agents naar composable plugins, kun je specialiseren.

De vraag die overblijft: welke state mag wel centraal blijven? MCP wordt stateless op protocolniveau, maar ergens moet sessie-context leven. Agents worden composable, maar de plugin-discovery-layer zelf is een single point of coordination. De grens verschuift — maar verdwijnt niet.
