De week van 24 mei brengt geen nieuwe frontier-doorbraken, maar drie releases die elk een ander deel van de agentic stack verzwaren. Claude Code verbetert hoe je plugins distribueert en hoe je agentic pipelines beveiligt. LangGraph lost een lang sluimerend schaalbaarheidsprobleem op in checkpointing. En in het open-weight landschap consolideert Kimi K2.6 zijn positie als de goedkoopste weg naar SWE-Bench-resultaten die closed modellen bijhouden.

De opvallendste gemeenschappelijke deler: al deze updates veronderstellen dat je agents niet in isolatie draait maar als onderdeel van een langere pipeline — met persistente state, gecoördineerde subagents en deployment over meerdere machines. De complexiteit verschuift van het model zelf naar de infrastructuur eromheen.

## Claude Code — Week 19: Plugin ZIP-distributie, Hard Deny en Effort-aware Hooks

Claude Code v2.1.128 tot v2.1.136 (uitgebracht 4–8 mei 2026) brengt drie features die samen een coherent beeld geven: je wil plugins programmatisch distribueren, agentic workflows strikt beveiligen, en hooks slimmer maken zonder extra configuratie.

**Plugin distributie via .zip en URL**

Plugins laden kon al via een lokale directory, maar nu accepteert `--plugin-dir` ook `.zip`-archieven en voegt `--plugin-url` een remote fetch toe:

```bash
# Laad plugin voor de sessie vanuit een hosted archief
claude --plugin-url https://intern.example.com/orion-plugin.zip

# Of lokaal gebuilde .zip
claude --plugin-dir ./dist/orion-plugin.zip
```

Het praktische gevolg: je kan een plugin in CI bouwen als archief, hosten op een interne URL, en per sessie laden zonder lokale installatie op elke machine. Voor Remote Routines-workflows waarbij Claude Code-sessies in cloud-containers draaien, elimineert dit de deployment-stap per environment.

**Auto Mode Hard Deny Rules**

Auto mode (de classifier die permission-prompts afhandelt voor veilige acties) krijgt een extra beveiligingslaag: `hard_deny` rules in `settings.json` blokkeren acties _onvoorwaardelijk_, ook als een allow-exception toepasselijk zou zijn:

```json
{
  "autoMode": {
    "hard_deny": [
      "Bash(git push --force*)",
      "Bash(rm -rf *)",
      "Bash(kubectl delete *)"
    ]
  }
}
```

Dit is een fundamenteel ander model dan de huidige allow/deny-logica: hard deny is een absolute barrière, geen prioriteitsregel. In productie-agentic-workflows waar Claude autonoom commits maakt, is dit de correcte aanpak — je wil dat destructieve acties _nooit_ automatisch worden uitgevoerd, ongeacht hoe de allow-regels geformuleerd zijn.

**Hooks op Effort Level**

Hooks zien nu het actieve effort level via het `effort.level` veld in de JSON-input én via `$CLAUDE_EFFORT` als environment variable:

```bash
#!/usr/bin/env bash
# PostToolUse hook: skip uitgebreide logging bij low effort
if [ "$CLAUDE_EFFORT" = "xhigh" ]; then
  ./scripts/log_tool_call.sh "$HOOK_TOOL_NAME" "$HOOK_INPUT"
fi
```

Dit laat je de overhead van zware side-effects — logging, monitoring, extra API-calls — schalen met de intensiteit van de Claude-sessie. Gecombineerd met `worktree.baseRef: 'fresh'` (ook nieuw in week 19), waarbij nieuwe worktrees altijd vanuit de remote default branchen in plaats van lokale `HEAD`, heb je fijnmazige controle over hoe geïsoleerd en hoe zwaar elke agentic sessie draait.

## Hermes / Open Source — Kimi K2.6: 1T MoE en 300-agent Swarm

Moonshot AI's Kimi K2.6 (uitgebracht 20 april 2026, vrij beschikbaar op Hugging Face) is momenteel het sterkste open-weight model op coding- en agentic benchmarks. De kernarchitectuur: 1 biljoen parameters totaal, 32 miljard actief per token via Mixture-of-Experts routing met 384 experts per laag (8 gerouted + 1 shared).

**Benchmarks**

| Benchmark | Kimi K2.6 | GPT-5.4 | Claude Opus 4.6 |
|---|---|---|---|
| SWE-Bench Verified | 80,2% | — | — |
| SWE-Bench Pro | 58,6% | 57,7% | 53,4% |
| BrowseComp (solo) | 83,2% | — | — |
| Terminal-Bench 2.0 | 66,7% | — | — |

Kimi K2.6 scoort op SWE-Bench Pro beter dan zowel GPT-5.4 als Claude Opus 4.6 — de twee meest gebruikte closed modellen voor coding-agents. Op de Artificial Analysis Intelligence Index scoort K2.6 54 punten, het hoogste van alle open-weight modellen en slechts drie punten onder de closed flagships.

**Agent Swarm-architectuur**

K2.6 bevat een eigen orchestration-laag die horizontaal schaalt naar 300 parallelle sub-agents met 4.000 gecoördineerde stappen per run — 3x meer agents en 2,7x meer stappen dan de vorige generatie K2.5. Een enkelvoudige complexe coding-taak kan tot 12 uur non-stop doorlopen. Het model gebruikt Multi-head Latent Attention voor KV-cache compressie en native INT4-quantisatie via Quantization-Aware Training:

- Volledige weights: ~1.185 GB (bf16)
- INT4 QAT: ~594 GB — ~2x inferentie-speedup
- Context window: 256K tokens
- Licentie: modified-MIT, commercieel gebruik toegestaan

**Prijs en toegang**

Via Moonshot API: $0,60/M input, $2,50/M output. Via OpenRouter: $0,74/$3,49. Ter vergelijking: Claude Opus 4.7 kost $15/M input — K2.6 is ruim 8x goedkoper voor input-intensieve workloads. Voor Orion-use cases waarbij je hoge volumes MCP-tool-calling verwacht, is K2.6 een serieuze kandidaat als goedkope worker-agent in een hybride multi-model pipeline. Zelfhosten vereist een high-end GPU-cluster voor de volledige bf16-versie, maar INT4 QAT brengt dit realistisch dichter bij kleinere setups.

## Open Source Tools — LangGraph v1.2: DeltaChannel en per-node Timeouts

LangGraph 1.2.0 (uitgebracht 11–12 mei 2026) lost twee concrete productie-pijnpunten op: checkpoint-opslag die exponentieel groeit bij lange agent-sessies, en pipelines die kunnen vastlopen op één trage tool-call.

**DeltaChannel: 41x checkpoint-reductie**

Het probleem: bij elke stap serialiseert LangGraph de volledige state naar de checkpointer. Een 200-turn coding agent accumuleert zo 5,3 GB aan checkpoint-data. DeltaChannel verandert dit door alleen incrementele deltas op te slaan:

```python
from langgraph.channels import DeltaChannel
from typing import Annotated

class AgentState(TypedDict):
    messages: Annotated[list, DeltaChannel(snapshot_frequency=50)]
    code_context: Annotated[str, DeltaChannel(snapshot_frequency=20)]
```

`snapshot_frequency=K` schrijft elke K stappen een volledig snapshot om read-latency bij herstel te begrenzen. Resultaat: dezelfde 200-turn agent neemt nog maar 129 MB op — een reductie van 41x. Upgrade is volledig backwards-compatible: bestaande threads werken door zonder migratie, want `DeltaChannel.from_checkpoint` behandelt een plain state-waarde automatisch als basislijn.

**Per-node Timeouts**

De tweede grote feature: individuele nodes kunnen nu een timeout krijgen zodat één trage MCP-tool-call de pipeline niet blokkeert:

```python
from langgraph.graph import StateGraph
from langgraph.errors import NodeTimeoutError

graph = StateGraph(AgentState)
graph.add_node(
    "fetch_external_data",
    fetch_data_node,
    run_timeout=30.0,   # max 30s actieve executie
    idle_timeout=10.0,  # max 10s wachten op I/O
)
```

Bij timeout gooit LangGraph een `NodeTimeoutError` en draagt controle over aan de geconfigureerde retry policy — writes van de mislukte attempt worden gecleared. De timeout werkt uitsluitend voor `async` nodes: synchrone nodes blokkeren de event loop en kunnen niet worden geïnterrupt. Streaming v3 is content-block-aware en aligned met het Claude streaming-formaat, wat custom adapters overbodig maakt bij Claude-gebaseerde LangGraph-pipelines.

## AI Builders — Nate Herk: Multi-Agent Architecturen in Claude Code

Nate Herk (oprichter van AI Automation Society, 305k+ leden) publiceerde op 12 mei 2026 een diepgaande praktijktutorial: *Multi-Agent Building In Claude Code*. De aanpak die hij demonstreert is direct herkenbaar voor wie met Orion of Remote Routines werkt: meerdere gespecialiseerde Claude Code-instanties parallel laten draaien, elk met eigen scope en tools, gecoördineerd via een orchestrator-agent.

De kern van zijn aanpak: gebruik `claude agents` (Agent View) om de live state van elke subagent te monitoren, definieer scherpe `--system-prompt` grenzen per agent zodat er geen scope-overlap is, en laat de orchestrator alleen beslissen _welke_ agent een taak krijgt — niet hoe die taak intern wordt uitgevoerd. Die scheiding van verantwoordelijkheden is wat multi-agent systemen onderhoudbaar houdt.

Wat zijn tutorial toevoegt aan de standaard documentatie: een concreet patroon voor context-isolatie via separate worktrees per subagent (relevant na het nieuwe `worktree.baseRef: 'fresh'`), en een communicatieschema waarbij agents via gedeelde bestanden informatie uitwisselen zonder directe koppeling. Minder theoretisch dan de officiële docs, meer gericht op werkende pipelines met realistische edge cases.

## Tot slot

Wat opvalt deze week: de tooling rondom agents wordt volwassener in dezelfde dimensies tegelijk — distributie (plugin .zip), veiligheid (hard deny), schaalbaarheid (DeltaChannel) en autonomie (Kimi K2.6 Agent Swarm). Dat suggereert dat de sector de fase van "agents die individueel werken" aan het afsluiten is en de fase van "agents in productie-architecturen" aan het inrichten.

De vraag die daarna overblijft: hoe ver laat je autonomie gaan voordat je inlevert op voorspelbaarheid? Kimi K2.6's 4.000-stap swarm en Claude Code's hard deny rules zijn in zekere zin elkaars antithesen — maximale autonomie aan de ene kant, expliciete grenzen aan wat agents zonder toestemming mogen doen aan de andere. De manier waarop je die balans kiest, bepaalt meer over je agentic architectuur dan welk model je gebruikt.
