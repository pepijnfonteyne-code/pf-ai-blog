De week van 27 mei brengt drie thema's samen die de architectuur van langlopende agents fundamenteel veranderen. Bij Anthropic komen de Managed Agents features uit research preview naar public beta — memory die verbetert over honderden sessies, een evaluatiemodel dat los staat van de agent zelf, en parallelle fleet-executie. Tegelijkertijd plaatst Mistral zijn coding agents volledig in de cloud met Mistral Medium 3.5 als open-weight backbone: asynchrone langlopende sessies die mid-task vanuit je lokale omgeving de cloud in gaan. En in de community documenteert Simon Willison een patroon dat productie-agents eigenlijk al jaren misten: structured truncation-handling wanneer een LLM-response halverwege stopt.

De rode draad is reliability in productie. Niet meer het eerste proof-of-concept draaien en stoppen — maar agents die weken of maanden coherent blijven, context niet verliezen, en falen graceful afhandelen. Dat is precies wat de drie verhalen van vandaag gemeen hebben.

## Claude Code — Managed Agents: Dreaming, Outcomes en Multi-Agent Orchestration

Op 7 mei lanceerde Anthropic drie nieuwe features voor Claude Managed Agents, waarvan Dreaming in research preview en de rest in public beta. Samen lossen ze drie problemen op die iedereen tegenkomt die langer dan één sessie met dezelfde agent werkt.

**Dreaming**

Dreaming is een geplande background-job die een memory store plus tot 100 eerdere sessies leest en een nieuw output memory store schrijft. De job draait op Opus 4.7 of Sonnet 4.6, mergeert dubbele memories, verwijdert verouderde entries en extraheert patronen die een individuele sessie nooit ziet. Het resultaat is een agent die na tientallen sessies niet langzamer wordt maar juist scherper — want de patterns uit week drie zijn beschikbaar in sessie zes.

```python
# Dreams API — aanroepen na het sluiten van een sessie-batch
client.beta.managed_agents.dreams.run(
    agent_id="agt_xxx",
    memory_store_id="ms_xxx",
    session_ids=recent_session_ids[-100:],  # max 100 sessies
    model="claude-opus-4-7",
    review_mode="auto"  # of "manual" voor handmatige review voor apply
)
```

`review_mode="manual"` stuurt voorgestelde memory-updates naar een review-queue voordat ze worden toegepast — nuttig als je strikte controle wil over wat de agent structureel onthoudt.

**Outcomes**

Outcomes lost een fundamenteel evalutieprobleem op: een agent die zijn eigen output beoordeelt, is beïnvloed door zijn eigen redenering. Outcomes gebruikt een aparte grader in een eigen context window, volledig los van de agent-sessie. Je schrijft een rubric met succesfactoren, de grader evalueert de output daartegen, en als iets niet klopt pinpointet het de delta — waarna de agent een nieuwe pass doet.

```yaml
# Rubric definitie voor een code-review agent
outcomes:
  criteria:
    - name: test_coverage
      description: "Alle publieke functies hebben minstens één unit test"
      weight: 0.4
    - name: no_security_issues
      description: "Geen OWASP Top 10 kwetsbaarheden geïntroduceerd"
      weight: 0.6
  max_iterations: 3
```

Dit patroon is direct inzetbaar voor Orion-workflows waar je nu handmatige kwaliteitscontrole doet na agent-runs. Twee tot drie iteraties halen in de praktijk de meeste systematische fouten eruit zonder oneindige loops.

**Multi-Agent Orchestration**

De fleet-definitie laat een lead agent taken opsplitsen en delegeren aan specialists met elk hun eigen model, prompt en toolset. Specialists delen een filesystem en dragen bij aan de context van de lead agent. Dat is de aanpak die grote repo-taken haalbaar maakt zonder alles in één context window te proppen.

```python
fleet = client.beta.managed_agents.fleets.create(
    lead_agent_id="agt_lead",
    specialists=[
        {"agent_id": "agt_test_writer", "role": "testing"},
        {"agent_id": "agt_doc_writer", "role": "documentation"},
    ]
)
```

Een bijkomende verbetering van deze week: de Agent SDK streaming-fix pakt een uncaught exception aan bij het einde van streaming sessions. Als je deze fleet-orchestration via de SDK monitort, zijn session lifecycle events nu betrouwbaar — silent failures bij session-end zijn voorbij.

## Hermes / Open Source — Mistral Medium 3.5 en Vibe Remote Agents

Mistral lanceerde op 29 april Mistral Medium 3.5, een dense 128B open-weight model met 256K context, als backbone voor Vibe Remote Agents. Het kernidee: coding sessions draaien niet meer lokaal maar asynchroon in de cloud, in parallel, zonder dat jij ernaar hoeft te kijken.

De "teleportatie" mechanic is technisch interessant: je start een sessie lokaal via de CLI of Le Chat, en halverwege de taak kan je de volledige context — task, vorige stappen, gemaakte wijzigingen — de cloud insturen. Vanaf dat moment gaat de agent autonoom verder terwijl jij iets anders doet.

```bash
# Start lokaal, teleporteer naar cloud mid-task
mistral vibe start --task "Refactor authentication module" --repo my-repo
# ... agent werkt lokaal ...
mistral vibe teleport  # volledige context naar cloud, sessie gaat door
```

Vibe integreert natively met GitHub (code + PR's), Linear en Jira (issues), Sentry (incidents) en Slack/Teams voor rapportage. De taken waarvoor het is gebouwd zijn eerlijk gedefinieerd: module refactors, test generation, dependency upgrades, CI investigations. Geen vage "doe alles"-claims.

Het SWE-Bench Verified score is 77.6% — lager dan Kimi K2.6 (80.2%) of Gemini 3.5 Flash (81.0%), maar het model is open-weight en self-hostable. Dat is de sleutelonderscheid met closed-source cloud-only tools: je kan Mistral Medium 3.5 lokaal draaien voor gevoelige codebases, en de Vibe cloud-laag er bovenop gebruiken alleen voor taken waar asynchroon draaien je workflow oplevert.

INT4 quantization maakt deployment op A100/H100 realistisch. De 256K context is voldoende voor de meeste repo-scans zonder chunk-strategieën te bouwen.

## AI Builders — Simon Willison en het truncation-handling patroon

Simon Willison documenteerde op 21 mei een patroon in zijn Datasette Agent dat de meeste SDK-integraties missen: structured truncation-handling wanneer een LLM-response halverwege afgekapt wordt.

Het probleem is bekend maar wordt zelden systematisch aangepakt. Als een agent een grote codebase analyseert of een lange test-output verwerkt, is de kans reëel dat de response stopt midden in een relevante sectie. Zonder expliciete handling wordt dat een silent failure: de pipeline gaat door met incomplete output alsof alles OK is.

Willison's aanpak in drie stappen:

1. Inspecteert `stop_reason` na elke API-call
2. Vergelijkt output tokens met het model-maximum
3. Als truncated: hervat de sessie met de vorige output als prefix en een expliciete continue-prompt

```python
def call_with_truncation_recovery(client, messages, model, max_tokens):
    response = client.messages.create(
        model=model,
        messages=messages,
        max_tokens=max_tokens
    )
    if response.stop_reason == "max_tokens":
        # Truncation detected — context uitbreiden en hernemen
        continuation_messages = messages + [
            {"role": "assistant", "content": response.content},
            {"role": "user", "content": "Continue from where you left off."}
        ]
        return call_with_truncation_recovery(
            client, continuation_messages, model, max_tokens
        )
    return response
```

Het patroon is model-agnostisch en werkt voor elke streaming SDK-integratie. Direct relevant voor Remote Routines of Orion-pipelines die grote outputs verwerken: code reviews, test-output parsing, documentatiegeneratie. Het is precies het soort infrastructuurlaag die het verschil maakt tussen een proof-of-concept en een agent die je vertrouwt om 's nachts te draaien.

Zijn liveblog van Code with Claude 2026 (6 mei) is ondertussen de meest geciteerde externe technische analyse van de Managed Agents aankondigingen — een nuttig tweede perspectief naast de officiële documentatie voor wie de implementatiedetails wil toetsen.

## Tot slot

De drie verhalen van vandaag wijzen in dezelfde richting: agent-infrastructuur die volwassen genoeg wordt voor productie. Dreaming lost context-verval op over sessies heen. Outcomes vervangt handmatige evaluatie door een principieel andere architectuur. Mistral's teleportatie-mechanic lost het "mijn laptop moet aan blijven staan"-probleem op. En Willison's truncation patroon vult de gaten die SDK-documentatie zelden behandelt.

De vraag die overblijft: op welk moment wordt het evaluatieproces zelf het bottleneck? Als Outcomes-rubrics de kwaliteit van agent-output bepalen, is de kwaliteit van die rubrics de nieuwe variabele om te optimaliseren. Dat is niet anders dan het schrijven van goede tests — maar voor agentisch gedrag is de ruimte van mogelijke outputs ordes van grootte groter.
