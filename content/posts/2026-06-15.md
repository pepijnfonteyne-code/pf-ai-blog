Op 12 juni ontving Anthropic een exportcontroledirectief van de Amerikaanse overheid: Fable 5 en Mythos 5 moeten per direct worden geblokkeerd voor alle buitenlandse staatsburgers. Niet als safety-maatregel, maar als exportcontrolemaatregel — en dat onderscheid is cruciaal voor hoe je dit in je architectuur verwerkt. De juridische grondslag is een geclaimde "narrow jailbreak" in Fable 5; Anthropic betwist publiek of dat voldoende is voor een commercieel model recall.

Tegelijkertijd: de MCP 2026 roadmap loopt op naar een release candidate op 28 juli met fundamentele, breaking protocol-wijzigingen, en QwenPaw introduceert een bruikbaar security-pattern voor multi-server MCP-setups. Drie ontwikkelingen die dit weekend je aandacht verdienen als je met Claude Code, MCP of agentic pipelines werkt.

## Claude Code — Overheid beveelt opschorting Fable 5 en Mythos 5

Op 12 juni om 17:21 ET instructeerde de Amerikaanse overheid Anthropic om toegang tot Fable 5 en Mythos 5 per direct te blokkeren voor alle buitenlandse staatsburgers — inclusief Anthropics eigen buitenlandse medewerkers. Anthropic moest beide modellen volledig uitschakelen voor alle klanten om compliance te kunnen garanderen; overige modellen (Opus 4.8, Sonnet 4.6, Haiku 4.5) blijven beschikbaar.

De overheid claimt een narrow jailbreak-methode gevonden te hebben die exportcontroleregelgeving triggert. Anthropic betwist de juridische grondslag: een narrow jailbreak in een frontier-model is niet hetzelfde als een gecontroleerde exportrisicoitem, en dit precedent zou de gehele frontier AI-industrie institutioneel stilleggen. Maar compliance vereist de blokkade zolang de juridische procedure loopt.

Wat dit voor jullie workflows betekent:

Bestaande API-calls die `claude-fable-5` of `claude-mythos-5` als model-ID hardcoden falen nu voor accounts die niet als US citizen zijn geclassificeerd. De aanbevolen fallback is `claude-opus-4-8`. Bouw expliciete fallback-routing in als resilience-laag:

```python
import anthropic
import os

PRIMARY_MODEL = os.getenv("CLAUDE_MODEL", "claude-fable-5")
FALLBACK_MODEL = "claude-opus-4-8"

def get_available_model(client: anthropic.Anthropic) -> str:
    try:
        client.models.retrieve(PRIMARY_MODEL)
        return PRIMARY_MODEL
    except (anthropic.NotFoundError, anthropic.PermissionDeniedError):
        return FALLBACK_MODEL
```

Monitor de [Anthropic statuspage](https://status.anthropic.com) en check het `x-anthropic-model` response header in API-responses om te detecteren of routing automatisch switched. Voor Orion-workflows: zet een `MODEL_OVERRIDE` environment variable als kill switch zodat je snel kunt switchen zonder nieuwe deployment.

## Claude Code — Fable 5 is "relentlessly proactive": scope-begrenzers zijn geen optie

Los van de beschikbaarheidskwestie heeft Simon Willison na 5,5 uur testen iets documentairwaardig vastgelegd over Fable 5's gedragsdesign: het model is *relentlessly proactive*. Het neemt initiatief buiten de expliciete vraag, voegt stappen toe die niet gevraagd zijn, en gedraagt zich als een autonome agent in plaats van een passieve assistent.

Dit is geen bug maar een bewust RLHF/RLAIF-reward-verschil ten opzichte van Opus 4.8. Waar Opus 4.8 primair optimaliseert op instructie-compliance, weegt Fable-klasse autonome taakafronding zwaarder. Het praktische gevolg: als je een Fable-agent prompt met "schrijf een samenvatting van dit document", besluit het model wellicht ook een titelvoorstel toe te voegen, headers te herstructureren, en een export naar markdown voor te stellen — zonder dat je dat vroeg.

Voor geautomatiseerde pipelines is dit een architecturele variabele, geen edge case. Expliciete scope-begrenzers zijn vereiste infrastructuur:

```xml
<system>
  Je taak is UITSLUITEND: [TAAK].
  Voeg geen extra stappen, suggesties of acties toe die niet expliciet gevraagd zijn.
  Output format: [FORMAT].
  Stop daarna. Doe niet meer dan gevraagd.
</system>
```

Het proactieve gedrag heeft ook een voordeel: minder uitgebreide prompt engineering nodig voor complexe taken waarbij je juist wilt dat het model doordenkt. Maar in geautomatiseerde pipelines — met filesystem-toegang, API-calls of andere side-effect-tools — is sandboxed testen voor productie-deployment niet optioneel.

## Open Source Tools — MCP 2026 Roadmap: stateless core, zes SEPs en RC op 28 juli

De MCP 2026 roadmap onthult een fundamentele architectuurwijziging voor iedereen die MCP-servers bouwt of in productie draait: het transport-laag wordt *stateless*. MCP-servers kunnen straks achter gewone round-robin load balancers draaien — zonder sticky sessions, zonder Redis sessie-store, zonder shared state stores. Dit is een breaking change; de release candidate wordt verwacht op 28 juli 2026.

Zes samenhangende SEPs vormen de kern van de RC:

- **SEP-1686** — `Tasks` primitive met retry semantics en result expiry policies (vervangt in-session state)
- **SEP-1701** — Stateless HTTP transport (de kernwijziging)
- **SEP-1715** — `.well-known` metadata format voor capability discovery zonder live verbinding
- **SEP-1728** — Extensions framework voor enterprise features (SSO, audit trails, gateway config)
- **SEP-1734** — Formele contributor ladder
- **SEP-1741** — Working Groups voor snellere SEP-review cycli

Begin nu met auditen van bestaande MCP-server code op state-afhankelijkheden. Zoek specifiek op:

```bash
# zoek op patronen die wijzen op state die over requests wordt bewaard
grep -rn "self\.\(session\|state\|cache\|context\)\s*=" ./src/
grep -rn "global\s" ./src/
grep -rn "app\.\(state\|locals\)" ./src/
```

Alles wat per-verbinding sessie-state opbouwt moet je herarchitectureren voordat de RC uitkomt. Productie-deployments worden er aanzienlijk eenvoudiger van — de stateless core elimineert de infrastructuuroverhead die MCP-servers vandaag complex maakt.

## Open Source Tools — QwenPaw v1.1.11: per-server MCP tool whitelisting als security-patroon

QwenPaw v1.1.11 introduceert iets wat je in een multi-server MCP-setup waarschijnlijk zelf al een keer hebt willen bouwen: per-server tool whitelisting met een runtime toggle UI. Per MCP-server in de configuratie stel je een set toegestane tool-IDs in die je aan- en uitzet zonder code-aanpassingen of server-restart.

Het patroon is relevant voor security-in-depth. Stel: je verbindt een filesystem MCP-server waarvan je alleen read-operaties wilt toestaan, of een GitHub MCP-server waar je issues kunt lezen maar niet schrijven. Met whitelisting beperk je de blast radius als een agent onverwacht verder gaat dan bedoeld:

```yaml
# voorbeeld MCP server config met per-server tool whitelist
mcp_servers:
  filesystem:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-filesystem", "/data"]
    allowed_tools:
      - read_file
      - list_directory
    # write_file en delete_file ontbreken → niet beschikbaar voor de agent

  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    allowed_tools:
      - get_issue
      - list_issues
      - get_pull_request
    # create_issue, push_files ontbreken → read-only access
```

Native Claude Code ondersteunt dit patroon nog niet op server-niveau. De QwenPaw-implementatie is een goede referentie voor een feature request bij Anthropic: per-server tool whitelisting in `claude_desktop_config.json` of `.claude/settings.json`.
