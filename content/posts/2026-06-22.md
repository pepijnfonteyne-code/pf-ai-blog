Simon Willison postte deze week een TIL die kort maar veelzeggend is: met één MCP-server-configuratie kan Claude Code een zichtbaar Chrome-venster openen en besturen via tekstcommando's. Geen externe orchestratie, geen Selenium-wrapper — gewoon `microsoft/playwright-mcp` als MCP-server in je `settings.json`.

Tegelijk komen er uit de open-source hoek twee modellen met een opmerkelijke capability/cost-ratio, en de MCP-specificatie werkt in zijn aankomende 2026-07-28 release candidate een set caching-headers uit die de stateless transitie completer maken dan de headline deed vermoeden.

## Claude Code — Playwright MCP als browser-interface

Het patroon dat Willison beschrijft is eenvoudig in configuratie maar breed in impact. Je voegt `@playwright/mcp` toe aan de `mcpServers`-sectie van je Claude Code settings en daarna kun je letterlijk schrijven: *"Use playwright mcp to open a browser to [url]"*. Claude Code opent een volledig zichtbaar Chrome-venster — geen headless — en stuurt het via de Playwright MCP-tools.

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["@playwright/mcp@latest"]
    }
  }
}
```

Dit opent workflows die voorheen externe tooling vereisten: UI-testing waarbij je Claude Code de visuele state laat beoordelen, web scraping met JavaScript-rendering, en formulierinteracties als onderdeel van een agentic run. In een Orion-context is het relevant voor elke taak waarbij een agent een webinterface moet navigeren of een live pagina moet evalueren — een deploy-dashboard controleren, form-output valideren, of een multi-step checkout doorlopen in een test-omgeving.

Het verschil met headless Playwright-scripts is niet technisch maar operationeel: de agent beslist zelf wanneer en hoe hij de browser gebruikt, op basis van de taak. Je schrijft geen script; je beschrijft een doel.

Willison beschrijft in dezelfde week ook een grens: hij probeerde Cloudflare-regels te bewerken via de Cloudflare MCP-server, maar die had niet de juiste operaties voor zijn use case. Zijn oplossing: overstappen op directe Cloudflare API-calls via Claude Code. Zie hieronder bij AI Builders voor de beslissingsvraag die dit stelt.

## Hermes / Open Source Models — VibeThinker-3B en Nemotron 3 Ultra

Twee open-source releases verdienen aandacht, al heeft geen van beiden een grand announcement gehad.

**VibeThinker-3B** (WeiboAI) is een fine-tune van Qwen2.5-Coder-3B, uitgebracht onder MIT-licentie. Op math- en code-reasoning benchmarks claimt het parity met frontier reasoners op specifieke taken. Dat laatste moet je met benchmark-scepticisme lezen, maar de combinatie is uitzonderlijk: 3B parameters, MIT-licentie, volledig commercieel inzetbaar, draait comfortabel op een M2-laptop of een kleine GPU instance.

```python
# Lokaal draaien via Ollama (zodra beschikbaar)
# ollama run vibethinker-3b

# Of via HuggingFace Transformers
from transformers import AutoModelForCausalLM, AutoTokenizer
model = AutoModelForCausalLM.from_pretrained("WeiboAI/VibeThinker-3B")
```

De MIT-licentie is hier het kritieke verschil met modellen als DeepSeek (eigen licentie) of commerciële API-afhankelijkheden. Voor productie-deployments waarbij compliance-overhead vermijden telt, of voor integratie in client-facing tools zonder API-kosten, is VibeThinker-3B een serieuze kandidaat voor reasoning-subtaken met lage latency-vereisten.

**Nemotron 3 Ultra** (Nvidia) speelt een ander spel: het scoort hoog op de capability-efficiency ratio op Nvidia GPU-hardware specifiek. De architectuur is geoptimaliseerd voor hoge throughput op H100/H200-setups. Als je een Nvidia-cluster hebt en hoge throughput nodig hebt, is het het onderzoeken waard — maar het is geen universeel alternatief.

In het Orion-landschap: gebruik VibeThinker-3B voor snelle, lokale reasoning-stappen waar privacy of latency zwaarder weegt dan absolute topkwaliteit. Koppel het aan Sonnet of Fable 5 voor de finale output als kwaliteit kritisch is — een hybrid pipeline waarbij de kleine model filtert en routeert, en het grote model alleen de complexe stappen uitvoert.

## Open Source Tools — MCP 2026-07-28: caching headers en W3C Trace Context

De headline van de MCP 2026-07-28 Release Candidate is het verdwijnen van sessies en `Mcp-Session-Id`. Maar de spec bevat twee toevoegingen die voor het bouwen van productie-MCP-services minstens even relevant zijn.

**Cache-headers op resultaten.** List- en resource-read-resultaten krijgen `ttlMs` en `cacheScope` velden, gemodelleerd naar HTTP Cache-Control semantiek:

```json
{
  "result": [
    { "uri": "file:///project/README.md", "name": "README" }
  ],
  "_meta": {
    "ttlMs": 300000,
    "cacheScope": "user"
  }
}
```

`cacheScope` kan `"user"`, `"session"` of `"global"` zijn. Dit geeft MCP-servers een expliciete manier om aan clients en intermediaries te communiceren hoe lang resultaten geldig zijn en voor wie ze gecached mogen worden. Zonder dit bouwden implementors ad-hoc caching-logica of deden helemaal geen caching. Nu is het onderdeel van het protocol.

Voor MCP-servers die resource-lists teruggeven die nauwelijks veranderen — denk aan een lijst van beschikbare tools of statische configuratie — is een hoge `ttlMs` met `"global"` scope een directe manier om onnodige round-trips te elimineren.

**W3C Trace Context in `_meta`.** Distributed tracing wordt formeel ondersteund via `traceparent`, `tracestate` en `baggage` in het `_meta`-veld:

```json
{
  "_meta": {
    "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
    "tracestate": "rojo=00f067aa0ba902b7"
  }
}
```

Dit betekent dat een request door een LLM-applicatie, via MCP naar een tool, via die tool naar een externe API, traceerbaar is als één coherente trace in standaard-observability-tooling (OpenTelemetry, Jaeger, Grafana Tempo). Voor wie MCP-servers in productie draait met meerdere downstream-afhankelijkheden is dit de brug naar échte distributed tracing zonder custom headers te hoeven introduceren.

**Wat dit vraagt van bestaande implementaties:** check of je code `Mcp-Session-Id` verwacht of `initialize`/`initialized` handshakes verwerkt. Als dat zo is, zijn dit de breaking changes voor de 2026-07-28 transitie. Tier 1 SDKs moeten support shippen binnen het 10-weken validatievenster na RC-publicatie.

## AI Builders — Wanneer MCP, wanneer directe API?

De Willison/Cloudflare-case brengt een patroon naar boven dat relevant is voor iedereen die Orion-workflows bouwt met MCP-servers. MCP is een abstractielaag — en elke abstractielaag heeft grenzen.

**Gebruik MCP als:**
- De operaties die je nodig hebt volledig gedekt zijn door de server
- Je van de tool-abstractie in een LLM-sessie wil profiteren (Claude roept tools aan op naam, niet op endpoint)
- De MCP-server actief onderhouden wordt voor de service die je target

**Gebruik directe API als:**
- De MCP-server de operaties niet implementeert die je nodig hebt
- De MCP-server een thin wrapper is zonder extra intelligentie of authenticatie-logica
- Latency en controle over de request-response cyclus kritisch zijn

Voor Orion specifiek: het is zinvol om per MCP-integratie te documenteren welke operaties gedekt zijn. Als je later een workflow bouwt die een operatie nodig heeft die niet in de MCP-server zit, weet je direct dat je naar de API moet. Dit voorkomt de situatie waarbij Willison zat: testen, falen, diagnose stellen, dan pas switchen — in een agentic run kost die cyclus tokens en tijd.

De Playwright MCP is juist een voorbeeld waarbij de abstractie wél de volle waarde biedt: de server abstraheert browser-state, click-events en DOM-navigatie volledig weg en geeft Claude Code een schone tool-interface. Dat is precies het gebruik waarvoor MCP bedoeld is.
